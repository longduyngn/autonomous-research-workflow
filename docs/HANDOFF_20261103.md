## 5. Review risks identified but NOT fixed before pause

These are review targets, not confirmed failed live behavior:

1. **Bridge release ordering:** `/release` calls `gate.release`, which can free the
   resource, then closes a forced shared transport under `clients_lock` outside the
   resource operation lock. A new owner may claim/use that transport in between.
   Review and test closing/resetting transport atomically before ownership becomes
   available, without deadlocking the gate. This is the highest-priority concurrency
   review after the fixture failure.
2. **Feedback visibility:** `_context` currently includes all rows returned by
   `conversation.feedback`, including unapplied rows. A message arriving between
   boundary application and context construction may appear in a role prompt before
   its revision is applied. Filter the prompt to applied feedback or explicitly
   separate pending feedback; keep full history intact.
3. **Multiple listeners:** intake uses an in-process lock and task/event DB
   idempotency; there is no cross-process conversation-model dispatch lease.
   Documentation requires one Discord listener. Task submission is deduplicated,
   but multiple listeners could duplicate conversational model calls/delivery.
4. `core/control.py` still contains unused prototype `feedback`/`conversations`
   tables/methods, superseded by `core/conversation.py`. Remove unused code only after
   reference checks; do not drop historical DB tables/data.
5. Review all old dispatch entry points (`get_Next_actionable_tasks`, scripts) for
   bypassing new waits. Production scheduler uses the updated atomic claim path.
6. End-to-end native/API provider retries, optional conversation model startup and
   old task-bundle compatibility still need careful integration review. Existing
   bundles were not regenerated; their integrity manifests can reject changed
   controller hooks. Do not rewrite old evidence to make a recovery pass.
7. Approval fingerprinting and CLI admin identity are deliberately for trusted local
   code. They do not prevent a hostile same-user shell from accessing controller DBs.
   Do not describe this as a multi-tenant authorization boundary.
